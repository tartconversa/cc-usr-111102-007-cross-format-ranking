# 跨业态推荐的反事实离线评估与约束重排

本项目在合成资料上实现一条可训练、可离线核验的推荐研究流水线：可解释流行度基线、使用业态与时段特征的学习排序器、带业态上限与闭店排除的约束重排，以及在已知记录策略下区分“预测排序质量”和“日志能支持的策略价值”的离策略评估（OPE）。

所有记录均为虚构，不能用于陈述真实商场经营结果。日志是观察性的；下面所有数值都是离线估计，不是线上因果收益的证明。

## 输入约定

每请求日志记录单个选中项目及候选集合，`logging_propensity` 是选中动作的已知记录概率（0 到 1）。`items` 为带 `known_at` 与 `effective_at` 的属性版本。`reward_click` 与 `reward_redeem` 为 0 或 1；目标策略结果只涉及单项目奖励。

fixtures 为资料目录，`src/impression_reader.py` 为读取入口，tests 为测试。输入在运行中保持不变；研究结果写入独立的 `.workspace-output` 目录。全部实现只依赖 Python 标准库（3.11+）。

## 流水线

    python -m src.pipeline --fixtures fixtures --output .workspace-output --check

输出 `.workspace-output/report.json` 与 `summary.md`。`--check` 运行内建自检，失败时返回非零退出码。常用参数：`--seed` 覆盖随机种子，`--max-exact-lists` 调整精确枚举预算。

## 设计要点

### 1. 输入校验与去重

- 同 `request_id` 重复上报，字段完全一致才保留一条；任何字段不同都抛 `DuplicateConflictError`，不做静默合并。
- `logging_propensity` 必须在 [0,1]；`selected_item` 必须在候选集内；候选不得重复；奖励只能是 0/1；缺失与 0 严格区分。
- 去重后按 `requested_at` 排序再切分。

### 2. 按请求时间切分

`train_end` / `validation_end` / `test_end` 来自 `policies.json`：`< train_end` 训练，`[train_end, validation_end)` 验证，`[validation_end, test_end)` 测试，之后不进入任何集合。切分以请求时间为唯一依据；去重后每请求一行，因此同一请求不可能跨集合。报告逐请求复核成员互斥与时间顺序。

### 3. 属性 as-of 版本

打分只使用请求时刻已生效（`effective_at <= requested_at`）且当时已登记（`known_at <= requested_at`）的最新版本。`effective_at` 早于 `known_at` 的版本在 `known_at` 前不可见。没有可见版本的候选标记为不可用并说明原因，不补业态、不回填未来状态。

### 4. 两个排序器

- **流行度基线**（`src/baseline.py`）：训练集上项目点击率的拉普拉斯平滑，冷启动取先验 1/2。完全可手算，先打印公式与计数。
- **学习排序器**（`src/ranker.py`）：纯标准库 L2 逻辑回归，特征为业态 one-hot、请求当地小时时段 one-hot、项目点击率/核销率（向先验收缩）、`log1p` 训练曝光量。特征统计只来自训练集，且每条训练行的项目率特征用留一法剔除本行结果，避免目标泄漏。超参数只在验证集上按 `1/propensity` 加权对数损失挑选，测试集不参与调参。

两个排序器都会在报告中给出权重、训练损失曲线和调参网格。

### 5. 约束重排与动作概率（关键设计）

合法列表 = 候选集中 as-of 时刻可见且营业的项目，同业态至多 `max_per_category` 个，长度 `k = min(list_size, 可填充上限)`。实际展示列表按分数降序填充，若无法填满则如实变短并给出原因（闭店、无可见版本、业态上限、可用候选不足）。

动作概率分两条精确可核验的路径，都包含“重排 + 最终抽取”两层：

- **部署展示策略**（主评估对象）：从最终列表均匀抽取一项，`π(a) = 1/|列表|`（a 在列表中），否则 0。无需枚举，误差为 0。
- **随机列表策略**：在全部合法列表上按 `softmax(列表平均分数/τ)` 加权再均匀抽取，`π(a) = Σ_{L: a∈L} w(L)/|L|`。温度 `τ` 是设计选择：越小越集中，边际概率越尖，支持越难保证；报告默认 `τ=0.10`，并在输出中给出每个动作的边际概率，便于检查是否出现接近 0 的动作概率。

`π(a)` 绝不是重排前的归一化分数。报告专门给出反例，展示二者会如何不同。

**计算预算**：合法列表数先用“按业态分组的动态规划”精确计数，不物化列表。若不超过 `max_exact_lists`（默认 50000），精确枚举，动作概率误差为 0，成本约 `合法列表数 × k`；否则用固定种子的约束拒绝采样（默认 4000 个合法列表），逐动作报告蒙特卡洛标准误与接受率，成本约 `样本数 / 接受率 × k`。报告给出每个请求所选路径、估计操作数与耗时。

### 6. 离策略评估与支持性

`src/ope.py` 报告 IPS、SNIPS、有效样本量（ESS）、覆盖、按请求 bootstrap 区间，裁剪结果单独列出并标注为有偏。

支持性判定分三层：

1. 先核验记录策略是否为候选集上的均匀随机（每行 `propensity == 1/|候选集|`）。核验通过时，候选集内每个动作的记录概率都已知且为正。
2. 目标策略在**日志零支持动作**（不在候选集，或已核验为确定性记录）上若有正概率，该部分价值不可识别：报告 `proven_zero_support`，拒绝给出完整策略收益，只给出已识别部分。
3. 若支持无法核验（记录概率未知的动作），报告 `support_unverified`，同样不称完整策略收益。

手算样本（`hand-1`、`hand-2`）的 IPS 应为 0.25、SNIPS 应为 1/3，流水线在自检中断言这两个值。

### 7. 演示项

- **时间穿越检查**：逐请求逐候选检查 as-of 版本，并给出反事实（用最新版本会把闭店前的 f 误判为闭店）。
- **不可支持策略**：目标只推荐日志从未曝光的新项目，判定为零支持并拒绝完整价值。
- **属性版本切换**：f 在 2026-10-20 起闭店；此前请求继续按营业版本处理。
- **冷启动**：合成新项目只获得中性先验与业态/时段效应，并展示若违规回填未来热门度会抬高多少分数。
- **无法填满列表**：3 个同业态候选、上限 2，展示最终长度与原因。

### 8. 明确不宣称的内容

- 日志不能证明线上因果收益；OPE 数值依赖记录策略与目标概率的给定假设。
- 离线评估对象是从最终列表均匀抽取一项的单项目策略，不是整页收益。
- 排序指标（MRR、加权对数损失）与策略价值是两个不同问题，报告分别呈现。
- 裁剪后的 IPS 是有偏估计量。

## 本地操作

Python 3.11 及以上，只依赖标准库。进入项目根目录：

    python -m src.impression_reader fixtures/impressions.jsonl
    python -m src.pipeline --fixtures fixtures --output .workspace-output --check

编译检查：

    python -m compileall -q src tests

测试：

    python -m unittest discover -s tests -v

## 固定运行环境

    docker build -t cross-format-ranking:local
    docker run --rm cross-format-ranking:local

容器默认运行测试（含端到端流水线与自检）。镜像使用完整内容摘要固定，研究输入随项目一起复制。
